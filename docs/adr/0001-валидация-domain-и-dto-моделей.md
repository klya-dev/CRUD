## Контекст проблемы
Неопределённость выбора. Все варианты подойдут, но какой самый лучший и реливантный.

## Факторы, влияющие на принятие решений

* Масштабируемость
* Разделение ответственности
* Читаемость
* Простота внедрения
* Механизмы по умолчанию
* Вызов валидации

## Рассмотренные варианты

* FluentValidation
* Валидация в setter'е
* DataAnnotation

## Решение

Основной механизм проверки данных - `FluentValidation`.<br>
Т. к. соответствует всеми факторами:
* Отличная масштабируемость - можно создавать сколько угодно валидаторов без изменения модели
* Разделение ответственности - класс модели не привязан к валидатору
* Читаемость - класс модели описывает модель, а валидатор - проверку данных
* Простота внедрения - добавить `Scoped` сервис
* Механизмы по умолчанию - много правил валидации по умолчанию, простота создания пользовательских правил
* Вызов валидации - ручной вызов валидации, с одной стороны это не удобно, с другой стороны это база масштабируемости, можно самому выбрать валидатор. Соответственно, вызов валидации нужно покрывать тестами.

Для Domain моделей валидатор не нужен, т. к. данные в базе не всегда будут совпадать с актуальным валидатором.
Например, есть пользователь в базе с `Username = qwerty100`, у валидатора `User` стоит, что можно использовать латиницу и цифры.

НО, принято решение изменить правило для `Username` в валидаторе, например убрать возможность вписывать цифры.
Получится, когда пользователь захочет обновить любое поле из `User`, например, `LanguageCode`, то валидатор выбросит исключение, т. к. `Username` невалиден (`qwerty100` - запрещены цифры).

Шаги:
1) Читается вся сущность из базы.
2) Обновляется нужное поле.
3) Перед записью валидатор проверяет ВСЮ сущность.
4) Выбрасывается исключение, т. к. загруженное значение из базы невалидно (для нового валидатора).

С DTO моделями похожая ситуация.
Например, у `UpdateUserDto` есть три обязательных поля - `Firstname`, `Username`, `LanguageCode`. Если у пользователя в базе `Username = qwerty100`, и, например, валидатор меняет правила для `Username` на отсутствие цифр, то, если пользователь захочет обновить только `Firstname`, ему нужно передать ВСЮ DTO и окажется, что `Username` невалиден.

С `UpdatePublicationDto` другая ситуация, у него `Title` и `Content` необязательные, значит пользователь может передать только то поле со значением, которое он хочет изменить и в итоге получится избежать ошибки валидации.<br>
Но если пользователь передаст свой текущий `Title`, который, например, на данный момент стал невалидным, то ошибка валидации, как и с `UpdateUserDto`.

Несколько вариантов решения этой проблемы:
1) Сделать поля необязательными (простая реализация `PATCH`).
2) Передавать значение полей с базы и проверять соответствие в валидаторе (например, если `Username` неизменился - игнорируем).
3) Создать несколько конечный точек для каждого поля (`/user/firstname`, `/user/username`) - разделить DTO.

Я решил остановиться на простой реализации `PATCH` - необязательные поля. Для `UpdatePublicationDto` реализовал, для `UpdateUserDto` не стал, останется в качестве примера.

## Плюсы и минусы каждого варианта

### FluentValidation

* +, хорошая масштабируемость
* +, разделение ответственности
* +, читаемость
* +, простота внедрения
* +, много правил валидации по умолчанию
* -, ручной вызов валидации

### Валидация в setter'е

* +, автоматический вызов валидации
* -, плохая масштабируемость (одна и та же модель может использоваться с разными правилами)
* -, нет разделения ответственности
* -, плохая читаемость
* -, простота внедрения (ручное описание всех правил)
* -, нет правил валидации по умолчанию

### DataAnnotation

* +, простота внедрения (ручное описание всех правил)
* +, много правил валидации по умолчанию
* +-, нормальная читаемость
* +-, полуавтоматический вызов валидации (например, ModelState в контроллере)
* -, плохая масштабируемость (одна и та же модель может использоваться с разными правилами)
* -, нет разделения ответственности
